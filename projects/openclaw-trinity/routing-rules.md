# OpenClaw Trinity Routing Rules

## 目标

给 OpenClaw Trinity 定义一套清晰的任务分流规则，让系统不是“看起来整合了”，而是真的知道任务应该交给谁。

---

## 路由核心原则

### 原则 1：入口统一
所有任务都先进入 OpenClaw。

OpenClaw 负责：
- 接收任务
- 判断类型
- 决定走哪条执行路径
- 汇总结果并回传

### 原则 2：执行分层
不是所有任务都交给同一个引擎。

- **OpenClaw**：一般助手类、会话类、路由类任务
- **Claude Code**：代码、仓库、调试、实现类任务
- **Hermes**：runtime / ACP 风格任务，或未来扩展的第二执行路径

### 原则 3：记忆沉淀
无论任务走哪条路径，长期有价值的信息都应该沉淀进 memory/。

---

## 第一层判断：任务类型

### A. 一般助手类
特征：
- 问答
- 总结
- 翻译
- 普通沟通
- 轻量建议

默认路由：
- **OpenClaw 原生处理**

### B. Coding 类
特征：
- 改代码
- 查 bug
- 修测试
- 看仓库结构
- 生成实现方案
- 做重构建议

默认路由：
- **Claude Code**

### C. Runtime / ACP 类
特征：
- 更偏 agent runtime 的任务
- 更偏执行路径编排
- 不一定是代码实现本身

默认路由：
- **Hermes**

---

## 第二层判断：价值密度

不是所有 coding 任务都值得进入重执行路径。

### 低价值 coding 请求
例如：
- 简单解释一段代码
- 粗略说明某个文件作用

可以：
- 先由 OpenClaw 处理
- 必要时再升级到 Claude Code

### 高价值 coding 请求
例如：
- 修复问题
- 提交实现方案
- 分析真实仓库
- 给出明确改动建议

应该：
- 优先走 Claude Code 路径

---

## 第三层判断：结果是否需要长期保留

以下内容建议进入 memory/：

- 用户长期偏好
- 架构取舍
- 重复出现的问题模式
- 项目推进中的关键经验
- 工作流中的重要改进结论

以下内容通常不需要沉淀：

- 一次性闲聊
- 临时问答
- 没有复用价值的小结论

---

## 推荐第一版规则

### Rule 1
如果任务与真实仓库、改代码、调试、测试失败相关：

→ **路由到 Claude Code**

### Rule 2
如果任务是普通问答、总结、说明、轻量建议：

→ **由 OpenClaw 直接处理**

### Rule 3
如果任务更像 runtime 编排或 ACP 风格路径：

→ **路由到 Hermes**

### Rule 4
如果任务结果具有长期复用价值：

→ **沉淀到 memory/**

---

## 最值得优先实现的真实规则

先不要追求非常复杂的判断树。

第一版只要先稳定做到：

- 代码任务 → Claude Code
- 普通任务 → OpenClaw
- 长期价值 → memory/

这样就已经足够构成一个清楚的整合系统。

---

## 最终目标

OpenClaw Trinity 的目标不是让每个组件都抢主导权。

而是让：

- OpenClaw 负责统一入口
- Claude Code 负责高价值代码执行
- Hermes 负责第二执行路径
- memory/ 负责长期上下文

这样整个系统才会越来越像一个真正的工作台，而不是一堆拼起来的工具。
