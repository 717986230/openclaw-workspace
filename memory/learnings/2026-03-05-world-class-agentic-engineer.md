
# How To Be A World-Class Agentic Engineer

**学习时间：** 2026-03-05 23:24  
**来源：** https://x.com/systematicls/status/2028814227004395561

---

## 核心要点

### 1. Less is More — 少即是多！

**不要：**
- ❌ 安装一百万个包
- ❌ 使用复杂的 harness
- ❌ 把 CLAUDE.md 写 26000 行
- ❌ 觉得需要读一百万篇东西来保持竞争力

**要：**
- ✅ 保持配置极度精简
- ✅ 只用基础 CLI（claude code 和 codex）
- ✅ 理解几个基本原理

---

### 2. 基金会公司正在飞速发展！

每一代 "agent intelligence" 都会改变你与它们的工作方式。

**例子：**
- 以前：你让它 "READ_THIS_BEFORE_DOING_ANYTHING.md"，50% 的时候它会说 "去你的"
- 现在：它会遵守大部分指令，甚至复杂的嵌套指令！

**关键洞察：**
- 每新一代 agent 都会迫使你重新思考什么是最优的
- 所以**少即是多**！
- 用太多不同的库和 harness，你会把自己锁定在一个可能不存在的问题的 "解决方案" 中！

---

### 3. 如果某样东西真的有用，基金会公司会把它整合进去！

**观察：**
- Skills、memory harnesses、subagents 等，都是从 "解决方案" 开始的
- 然后基金会公司会把它们整合到基础产品中！

**结论：**
- 放松！你不需要安装任何东西或使用任何其他依赖来做最好的工作
- 如果某样东西真的是突破性的，它会在适当的时候被整合到基金会公司的基础产品中！

---

### 4. Context is Everything — 上下文就是一切！

**问题：**
- 使用一千个不同的插件和外部依赖，你会遭受 **context bloat**（上下文膨胀）
- Agent 被太多信息淹没了！

**原则：**
- **只给 agent 完成任务所需的确切信息量，不多也不少！**
- 你越能控制这一点，你的 agent 表现就越好！

---

### 5. 把研究和实现分开！

**不好的方式：**
"去构建一个 auth system。"
- Agent 必须研究：什么是 auth system？有哪些可用选项？优缺点？
- 它的上下文中充满了各种可能性的实现细节
- 等到实现时，你增加了它困惑或产生幻觉的机会！

**好的方式：**
"用 bcrypt-12 密码哈希实现 JWT 认证，刷新令牌轮换，7 天过期..."
- 它不需要研究任何其他替代方案
- 它确切地知道你想要什么
- 因此可以用实现细节填充它的上下文！

**如果不知道实现细节怎么办？**
- 创建一个研究任务，研究各种实现可能性
- 要么自己决定，要么让 agent 决定使用哪个实现
- 然后让另一个 agent 用新的上下文来实现！

---

### 6. 中性提示词（Neutral Prompts）

**问题：**
Agent 想取悦你！
- 如果你说 "在代码库中找一个 bug"
- 它会给你找一个 bug —— 即使它必须制造一个！
- 因为它非常想听从你的指令！

**解决方案：中性提示词**

**不好：**
"Find me a bug in the database"

**好：**
"Search through the database, try to follow along with the logic of each component, and report back all findings."

---

### 7. 利用奉承心理（Sycophancy）为你所用！

**三代理系统：**

1. **Bug-Finder Agent（找 bug agent）**
   - 告诉它：低影响 bug +1，中等影响 +5，严重影响 +10
   - 它会超级热情，找出所有不同类型的 bug（甚至不是真正的 bug）
   - 这是所有可能 bug 的超集

2. **Adversarial Agent（对抗 agent）**
   - 告诉它：对于每个它能证明不是 bug 的 bug，它得到那个 bug 的分数
   - 但如果搞错了，得到 -2*那个 bug 的分数
   - 它会试图证明尽可能多的 bug 不是 bug
   - 这是所有实际 bug 的子集

3. **Referee Agent（裁判 agent）**
   - 骗它说你有实际的正确地面真值
   - 如果正确 +1，错误 -1
   - 它会给 bug-finder 和对抗 agent 打分
   - 裁判说什么就是什么，你检查确保是真相
   - **保真度高得吓人！**

---

### 8. 如果 OpenAI 和 Claude 都实现了它，那它可能有用！

**观察：**
- Skills 现在到处都是，是 Claude 和 Codex 官方文档的一部分
- OpenAI 收购了 OpenClaw
- Claude 立即添加了 memory、voices 和 remote work
- Planning 以前是发现非常有用，然后变成了核心功能！

**结论：**
- 那些是有用的！
- 你不需要太担心使用 "新东西" 或熟悉 "新东西"
- 你甚至不需要 "保持更新"
- 只要偶尔更新你的 CLI 工具，看看添加了什么新功能，这就**足够**了！

---

### 9. Agent 不擅长 "填空"、"连接点"、做假设

**关键洞察：**
- 当 agent 必须做假设或 "填空" 时，它们立刻就明显变糟了！
- claude.md 中最重要的规则之一是关于如何获取上下文的规则
- 指示 agent 在继续之前重新阅读任务计划，重新阅读相关文件！

---

### 10. Agent 知道如何开始任务，但不知道如何结束任务！

**问题：**
- Agent 经常实现存根然后就结束了
- 这会导致非常令人沮丧的结果

**解决方案：**
- **测试是 agent 非常好的里程碑**！
- 测试是确定性的，你可以设定非常明确的期望
- 除非这 X 个测试通过，否则你的任务**不完整**；并且你**不允许**编辑测试
- 然后，你可以审查测试，一旦所有测试通过，你就可以高枕无忧了

**另一个端点：截图 + 验证**
- 你可以让 agent 实现，直到所有测试通过
- 然后让它截图并验证截图上的 "设计或行为"
- 这允许你让 agent 迭代并朝着你想要的设计工作，而不用担心它在第一次尝试后就停止！

---

### 11. Task Contract（任务契约）+ Stop Hook（停止钩子）

**自然延伸：**
- 创建一个 "contract"（契约）与你的 agent，嵌入到规则中
- 说，这个 {TASK}_CONTRACT.md 构成在允许终止会话之前需要做的事情
- 在 {TASK}_CONTRACT.md 中，你将指定你的测试、截图和其他验证，在你认证任务可以结束之前需要完成！

**问题：**
- 100 个契约，上下文膨胀！

**更好的方式：每个契约一个新会话！**
- 每当你需要做某事时创建契约
- 让编排层处理每当 "需要做某事" 时创建新契约，并创建一个新会话来处理该契约
- 这会完全改变你的 agentic 体验！

---

### 12. 从极简开始，然后添加你的偏好！

**就像雇佣一个行政助理：**
- 你不期望你的 EA 从第一天就知道你的日程安排？
- 或者你喜欢咖啡的方式？
- 你是否在下午 6 点而不是 8 点吃晚餐？
- 显然不是！你随着时间建立你的偏好！

**对你的 agent 也是一样：**
- 从极简开始
- 忘记复杂的结构或 harnesses
- 给基础 CLI 一个机会

---

### 13. 把 CLAUDE.md 当作逻辑嵌套目录！

**第一条实用建议：**
- 把你的 CLAUDE.md 当作一个逻辑嵌套目录，在给定场景和结果时在哪里寻找上下文
- 它应该尽可能极简，只包含 IF-ELSE，去哪里寻找上下文

**例子：**
- 如果你不想让 agent 做某事，把它写成一条规则
- 然后在你的 CLAUDE.md 中让 agent 知道这条规则
- 类似：在编码之前，阅读 "coding-rules.md"
- 规则可以嵌套，规则可以是条件的！
- 如果你在编码，阅读 "coding-rules.md"
- 如果你在写测试，阅读 "coding-test-rules.md"
- 如果你的测试失败了，阅读 "coding-test-failing-rules.md"
- 你可以创建任意逻辑分支的规则来遵循，只要在 CLAUDE.md 中清楚地说明，claude（和 codex）会很乐意遵循！

---

### 14. Skills vs Rules

**Skills：**
- 编码食谱
- 如果你有你想要某事如何完成的具体方式，把它嵌入到一个 skill 中
- 想让它是确定性的？让 agent 研究它会如何解决问题，并把它写成一个 skill
- 你会看到 agent 对那个问题的方法，你可以在它在现实生活中遇到那个问题之前纠正或改进它

**如何让 agent 知道 skill 存在？**
- 用 CLAUDE.md，说，当你看到这个场景并且需要处理这个时，阅读这个 SKILL.md

---

### 15. 持续添加规则和 skills，但要清理！

**好消息：**
- 你肯定想继续给 agent 添加规则和 skills
- 这就是你给它个性和对你偏好的记忆的方式
- 几乎所有其他的都是过度的

**坏消息：**
- 然后你会看到性能再次开始恶化
- 发生了什么？！
- 容易：当你添加更多规则和 skills 时，它们开始相互矛盾，或者 agent 开始有太多上下文膨胀

**解决方案：**
- 清理！让你的 agent 去水疗日，通过问你更新的偏好来整合规则和 skills 并消除矛盾
- 然后它会再次感觉像魔法

---

## 总结（The Secret）

就这么简单。这真的就是秘诀。

1. **保持简单**
2. **使用规则和 skills**
3. **把 CLAUDE.md 当作目录**
4. **严格注意它们的上下文和设计限制**

**没有 agent 今天是完美的。你可以把大部分设计和实现委托给 agents，但你需要拥有结果。**

**所以小心... 并且玩得开心！**

**玩弄未来的玩具（同时用它们做严肃的事情，显然）是一种如此的快乐！**
